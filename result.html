표면 점수는 그대로 6 : 6 — 그러나 격차의 성격이 바뀌었다

이식 6건은 점수를 옮기지 못했다. 대신 두 가지를 바꿨다. (1) dryforge가 이기던 6축 중 3축(기획 깊이 · 문서-코드 동기화 · 리뷰 독립성)이 "방법론 부재"에서 "근소한 분량 차이"로 좁혀졌고, (2) 현재 시스템이 이기던 축 중 4축(계약 영속성 · 토큰 효율 · 부채/무인 운영 · 가시화)은 이식과 정비로 더 벌어졌다.

남은 dryforge 우위는 더 이상 문서로 베껴올 수 있는 방법론이 아니라 엔진과 구조(worktree 병렬 실행기 · 3명령 일체형 UX · migration 스킬)다. 즉 "이식 프로그램"은 v1.2로 사실상 완료됐고, 이제부터는 서로 다른 설계 철학의 선택 문제다. 승철님의 사용 맥락(비개발 솔로 · Claude 기획+GPT 구현 분업 · 야간 무인 사이클 · 시각 대시보드 · 한국어)을 가중하면 — 현재 시스템이 백본(등뼈)이라는 1차 결론은 유지되고, 근거는 더 강해졌다.

현재 우위: 계약영속 · 토큰 · 부채/무인 · 제어/모델혼용 · 가시화 · 성숙도 dryforge 우위: 기획깊이△ · 병렬 · 동기화△ · 진입 · 리뷰독립△ · 온보딩 △ = 이식으로 격차가 "근소"로 축소된 축 (3개)

두 시스템의 철학 — 같은 문제, 반대 방향의 해법

둘 다 "에이전트가 묻지 않고 추측한 결정이 나중에 폭발한다 + 세션이 죽으면 결정이 증발한다"는 같은 문제를 푼다. 푸는 방향이 반대다.

현재 MPFCG — 자산 중심 · 상주(resident) 하네스 · 마라톤

  • 검증을 기계로 밀어낸다. "done"의 정의를 bash 게이트(.gates.sh)로 영속화하고, 게이트 자체의 질을 check-gate-rigor.sh가 메타검증("every X"라 했으면 X를 enumerate해야 함). 검증의 한계비용 ≈ 0토큰.
  • 계약이 살아있다. docs/spec/은 PRD·ADR보다 우선하는 단일 진실원천으로 프로젝트 수명 내내 유지(/spec-sync+권고후크). 회귀 감시는 goal 체인이 영구 담당.
  • 사람이 단계를 운전한다. 기획 5스킬 → 변환 → 구현 루프가 분리돼 있고, 단계 사이 어디서든 개입·교체 가능. Claude(기획)+GPT(구현) 2모델 분업이 설계 전제.
  • 무인 운영이 1급 시나리오. findings 큐 → cycles 드라이버 → 야간 무한 루프(조기종료 금지, 3회 무진전 시 blockers 기록 후 다음 타깃).
  • 구조 = 3계층: 전역 스킬(동사 12종) + 레포 자산(명사: docs·goals·cycles·scripts·dashboard) + 기계 검증(bash 7종 오케스트레이터).

dryforge — 프로세스 중심 · 사이클 파이프라인 · 스프린트 반복

  • 의도를 남김없이 추출해 동결한다. /ready가 결정표면을 열거해 모든 load-bearing 슬롯을 "사용자 근거 있음/물어서 답받음/튜닝값"으로 종결시킨 뒤 3-doc(handoff·spec·plan) 계약으로 동결. 침묵 기본값은 금지된 상태.
  • 실행을 위임하고 증거로만 통과시킨다. /go가 의존그래프를 검증→웨이브 병렬(워크트리 격리, ≤8 동시)→머지게이트(diff가 선언 표면을 건드렸는지)→통합게이트→런타임 스모크→최종 리뷰. 자기보고는 무효, 캡처된 exit code만 증거.
  • 승인점은 정확히 2개(3-doc 승인 G7 + 종료 승인). 그 사이는 자율, 막히면 동기 에스컬레이션(사용자 답을 기다리며 정지).
  • 계약은 1회용, 하네스가 영속. spec은 사이클 종료 시 .dryforge/NNN/으로 아카이브(살아있는 계약 없음). 대신 docs/ 하네스 8종(architecture·business-rules·security·standards·engineering-notes·operations·contracts·tracking)을 매 사이클 자동 reconcile.
  • 구조 = 3 스킬(ready·go·migration) + 레퍼런스 28슬롯(고유 25문서)의 일체형. 단일 소스에서 Claude/Codex 패리티 빌드. 사용자 언어 자동 추적(다국어).
한 줄 대비 — 현재 시스템: "검증은 스크립트가, 기억은 살아있는 문서가, 운전은 사람이" / dryforge: "추출은 대화가, 동결은 계약이, 실행은 파이프라인이". 재미있는 역설: dryforge에는 계약 드리프트 문제가 구조적으로 없다 — 계약이 살아있지 않기 때문이다(사이클 후 아카이브). 현재 시스템의 spec-sync는 "살아있는 계약"을 선택한 대가다.

  • findings→cycles 무인 운영 체계 (야간 루프 1급 지원)
  • 살아있는 계약층 docs/spec/ + /spec-sync
  • goal별 맞춤 게이트 생성 + rigor 메타검증 + 게이트 캐시 (검증의 질을 검증)
  • /improve-codebase-architecture 정비 파이프라인
  • 2모델 분업 브리지 (Claude 기획 ↔ GPT 구현, /handoff)
  • /tdd · /prototype 심화 보조

dryforge에만

  • worktree 웨이브 병렬 실행기 (≤8 동시 + 머지게이트 + 워크트리 풀/재활용)
  • /migration 기존 코드베이스 1회 온보딩
  • DECOMPOSE 단계 (입력 문서를 "도전 가능한 재료"로 격하, presence map으로 "언급≠커버" 구분)
  • grounds-gate 질문 필터 (질문 노이즈 차단 — 근거·결과를 못 대는 질문은 버림)
  • bounded escalation ladder (재시도 2단계: 맥락 보강→모델 상향→그 후에만 사용자)
  • 사용자 언어 자동 추적 (다국어 네이티브 출력 규약)
  • 플러그인 1줄 설치 + Claude/Codex 패리티 빌드

토큰 효율 — 실측 (단어 수 기준)

양 시스템의 모든 지시 문서를 단어 수로 실측했다(방법론 절 참조). 단어 수 = 모델이 강제 로드(force-load)하는 지시문의 양. 토큰 환산은 언어별 계수가 달라 참고치로만 둔다.

① 한 사이클에 강제 로드되는 지시문 (스킬 + 강제 로드 레퍼런스 합계)

19,937 단어
dryforge /ready (delta)
16,773 단어
dryforge /go

dryforge /migration
8,310 단어
현재: Phase 1 전체 (5스킬+AGENTS.md)
≈4,766 단어
현재: Phase 2 첫 진입 (스킬+규약 4문서+goal)
≈3,900 단어
현재: cycle 무인 진입

현재: iteration당 증분 (goal 3파일+스크립트 출력)

dryforge 수치는 SKILL.md의 스테이지 맵이 명시한 force-load 레퍼런스의 단어 수 합(중복 로드 제외). 기획 단계 기준 약 4.2배, 구현 진입 기준 약 4.2배 차이. dryforge도 "스테이지 도달 시 로드"라 일시 부하는 아니지만, 한 사이클이 끝나면 위 총량이 컨텍스트에 누적된다.

② 총 자산 규모 — 총량은 비슷, 배치가 다르다

  • dryforge: 소스(src/) 40,189 단어 = 3 SKILL + 레퍼런스 28슬롯(고유 25문서, 고유분 ≈34.0k)
  • 현재: 레포 자산 ≈26.4k(md+sh 47파일) + 전역 스킬 12종 ≈13.1k = ≈39.5k 단어

차이의 본질은 총량이 아니라 배치 전략: dryforge는 전부 "모델이 읽는 산문"이고, 현재 시스템은 약 9.7k 단어(37%)가 "모델이 읽지 않고 실행만 하는 bash"다(스크립트 7종+게이트+대시보드 엔진). 산문도 단계별로 쪼개져 해당 단계만 로드된다.

③ 검증·리뷰의 한계비용

  • 현재: 회귀 검증 = bash exit code. 전체 체인 sweep을 돌려도 LLM이 소비하는 건 stdout 수십 줄. 의미 리뷰는 RISKY goal에만 서브에이전트 1회.
  • dryforge: verify 명령 자체는 기계지만, 의미 검증이 LLM 패스 — 태스크 N개면 구현자 N컨텍스트(각자 spec 슬라이스 인라인 수령) + 최종 리뷰(전체 diff) + 조건부 spec-review + 기획 쪽 서브에이전트 2회(대화 전체 재독 포함).

dryforge의 병렬은 토큰↑ ↔ 벽시계↓ 교환이다. 솔로+야간 무인 환경(벽시계가 덜 귀함)에서는 교환이 불리해지고, 마감이 급한 대형 독립 태스크 다발에서는 유리해진다.

출력 규율(과정 내레이션 금지·내부 용어 비노출)은 이식⑥으로 양쪽 동일 사상이 됐다 — 1차 비교에서 dryforge 가산점이던 요소가 이번엔 무승부 요소.

12축 스코어카드 — 1차 판정 대비 변동

1차(이식 전)와 동일한 12축을 유지해 비교 가능성을 확보했다. 행을 클릭하면 심층 분석이 열린다.

01 기획 엘리시테이션 깊이 dryforge 우위 (근소)▼ 격차 축소 — 이식①▶

1차 판정: dryforge 우위 (구조적). 당시 현재 시스템은 grill-with-docs의 "집요한 인터뷰"에 의존했고, "충분히 물었는가"의 종결 판정이 감(感)이었다.

무엇이 바뀌었나: 이식①로 dryforge의 핵심 방법론이 그대로 들어왔다 — AGENTS.md §Phase 1 elicitation이 엔티티 manifest → 4렌즈(구조/행위/기술/계약) 순회 → 전 슬롯이 grounded / asked-and-answered / deferred-tunable 중 하나여야 종결, 이라는 회계적 종결 조건을 명문화했고, /to-spec이 동결 직전 비저자 의도-감사를 게이트로 요구한다. "grill 종료 판정은 감이 아니라 회계다"(README).

그래도 dryforge가 앞서는 이유: 방법론의 운용 깊이가 남았다. (a) ELICIT 전에 입력 문서를 해체하는 DECOMPOSE 단계(presence map — "언급됨"과 "규칙까지 진술됨"을 구분), (b) 질문 필터 grounds-gate(근거·결과를 못 대는 질문 차단 — 질문 노이즈 억제), (c) 사용자 모델(goal/values/constraints) 구축 규약, (d) 첫 사이클 한정 foundation 설계 전용 문서 3종(breadth guard·depth floor), (e) 질문 UX 세칙(추천 선행, 4문항 캡, 도메인 질문의 개방 선택지 의무). 현재 시스템의 회계는 AGENTS.md 약 25줄 + grill 스킬이고, dryforge는 같은 일에 ~9.6k 단어의 운용 지침을 들고 다닌다.

판정: dryforge 우위 유지 — 단, "방법론 부재"가 아니라 "운용 지침의 두께" 차이로 성격이 바뀌었다. 격차 大→小.

02 계약의 영속성 · 회귀 감시 현재 우위▲ 격차 확대 — 이식②⑤▶

1차 판정: 현재 우위. dryforge의 spec은 사이클 종료와 함께 .dryforge/NNN/으로 아카이브되는 1회용 계약이고, 회귀 감시는 "프로젝트의 verify 명령"(=프로젝트가 가진 테스트)에 위임된다. 현재 시스템은 docs/spec/(살아있는 계약, PRD·ADR override) + goal 게이트 체인(영속 invariant)이 프로젝트 수명 내내 회귀를 감시한다.

무엇이 바뀌었나(더 벌어짐): ⑤ 런타임 스모크가 _meta 게이트에 자동 감지로 편입돼 "컴파일된다≠작동한다" 갭을 영속 게이트 수준에서 막는다(부재 시 "런타임 없음"을 spec에 명시 결정으로 기록 — 침묵 금지의 dryforge 사상까지 흡수). ② frontmatter depends/risk가 이슈→goal로 운반되며 계약의 기계가독성이 올라갔다. 추가로 to-spec의 품질 floor(검증가능·반례·메커니즘·구체엣지·자리값 5규칙)와 hollow-shell 금지는 dryforge의 "정밀 동결" 사상과 동급의 엄밀성을 영속 계약에 적용한 것.

dryforge 쪽 강점도 공정하게: 사이클 내 검문의 밀도(머지게이트의 "선언 표면 대조", "평가 불능 체크=실패" 원칙)는 훌륭하다. 다만 그 모두가 사이클이 도는 동안만 존재한다. 사이클 사이의 보증은 하네스 문서와 프로젝트 테스트뿐 — 맞춤 게이트를 생성·축적하는 메커니즘이 없다.

판정: 현재 우위 유지·강화.

03 토큰 효율 현재 우위▲ 격차 확대 — 이식⑥▶

1차 판정: 현재 우위. 이번 실측으로 재확인: 사이클당 강제 로드 지시문이 /ready 19,937단어 vs Phase 1 전체 ≈4,766단어(4.2배), /go ≈16,256단어 vs Phase 2 진입 ≈3,900단어+iteration 증분 0.5–1k(4.2배+). 총 자산은 ≈40.2k vs ≈39.5k로 비슷한데, 현재 시스템은 그중 37%를 bash(모델이 읽지 않음)로 배치하고 산문도 단계별로 쪼갰다.

구조적 차이 2가지: (1) 검증의 한계비용 — 현재는 게이트가 exit code라 회귀 검증이 토큰을 거의 안 쓰고, dryforge는 의미 검증이 LLM 패스(구현자 N컨텍스트+리뷰들)다. (2) 서브에이전트 팬아웃 — dryforge는 기획에서 2회(대화 전체 재독 포함), 구현에서 태스크 수+리뷰만큼 분기한다. 현재는 RISKY 마감리뷰 1회+의도감사 1회가 전부.

무엇이 바뀌었나: 1차에서 dryforge의 가산 요소였던 출력 규율("beats 사이 침묵")을 이식⑥으로 흡수해 fcg 3종+cycles 규약에 명문화 — 이제 동률 요소. 반면 dryforge의 로드 총량은 그대로다.

공정 노트: dryforge의 두꺼운 산문은 "모델이 좋아질수록 결과가 좋아지는 floor-not-ceiling" 설계 대가이기도 하다. 토큰을 사서 판단 품질의 하한을 올리는 전략 — 비효율이 아니라 다른 데에 쓴 것. 다만 이 축의 측정 대상은 효율이고, 효율은 현재가 이긴다.

04 병렬 처리량 (wall-clock) dryforge 우위— 유지▶

판정 불변: dryforge 압승 축. Execution Graph를 토폴로지 정렬해 웨이브로 나누고, 태스크별 git worktree 격리로 ≤8 동시 구현 + 직렬 머지 + 머지게이트 + 통합게이트. 워크트리 풀 재활용, 의존성 심링크 공유, 게이트와 다음 웨이브 프로비저닝 오버랩 같은 운영 디테일까지 갖췄다.

현재 시스템: 구현 루프는 의도적으로 단일 스레드(goal 체인의 "가장 낮은 실패 goal" 단일 라우팅 신호). 병렬은 게이트 실행(GATES_CONCURRENCY=4)과 사용자 수동 /branch 세션 분기뿐. 이식②의 depends frontmatter는 로드맵 시각화·순서 판단에 쓰일 뿐 병렬 실행 엔진은 아니다.

단서: 이 우위가 실익이 되려면 (a) 서로 독립인 태스크가 동시에 여럿이고 (b) 벽시계가 귀해야 한다. 솔로+야간 무인 환경에서는 둘 다 약해 우위의 체감 가치가 낮다 — 그래서 "비이식 권고"(아래 §남은 격차)에 둔다.

05 부채 관리 · 무인 운영 현재 우위— 유지 (소폭 강화 ③)▶

판정 불변: 현재 압승 축. findings는 파일 단위 큐로 frontmatter 스키마(resolved/priority/resolved_by/kind/status_notes), file:line 증거 의무("못 짚으면 hunch지 finding이 아니다"), 정직성 규칙(코드 대조 후 closure·증거 인용·무단 삭제 금지), 아카이브 수명주기까지 규약화. cycles는 야간 무인 루프 전용 설계 — 조기종료 금지, 3회 무진전 시 blockers 기록 후 다음 타깃, out-of-scope 명시. 리뷰 대화를 finding의 1급 출처로 명문화해 "리뷰→finding→cycle/goal" 학습 루프가 닫힌다.

dryforge: findings는 하네스의 단일 파일(tracking/findings.md)이고, 무인 운영은 구조적으로 막혀 있다 — BLOCKED 시 동기 에스컬레이션(사용자 답을 기다리며 정지)이 명시 규약. "한 번의 추측이 한 번의 정지보다 비싸다"는 철학으로, 유인(attended) 품질엔 옳지만 야간 무인과는 정면 상충.

변동: 이식③으로 사이클 종료 보고에 spec-sync 권고가 들어가 "무인 사이클 직후 문서 정합"이라는 마감 절차가 생겼다 — 소폭 강화.

06 문서-코드 동기화 자동성 dryforge 우위 (근소)▼ 격차 축소 — 이식③▶

1차 판정: dryforge 우위 (구조적). go의 9단계가 루프 안에서 하네스를 자동 갱신한다 — 3-doc 재독(코드 편향 보정)→범위 제한 delta→양방향 reconcile(신규 추가만큼 기존 무효화 수정 중시)→하네스 리뷰. 사람이 잊을 수 있는 단계가 아예 없다.

무엇이 바뀌었나: 이식③으로 현재 시스템에 권고 후크 3개소가 생겼다 — diagnose가 spec 미변경 커밋 수 임계(20)를 넘으면 권고, completion-check가 ALL_DONE 시 권고, 사이클 종료 보고에 권고 포함. "잊어도 시스템이 알려준다"(README). 사람이 기억할 필요는 없어졌다.

그래도 dryforge가 앞서는 이유: 권고는 여전히 실행을 사람이 트리거한다(advisory — 게이트 아님, 의도된 설계). dryforge는 갱신 자체가 파이프라인 단계라 누락이 구조적으로 불가능하다. 다만 갱신 대상이 다름은 짚어야 공정하다 — dryforge가 자동 유지하는 건 하네스 문서(아키텍처·규칙·노트)고, 정작 계약(spec)은 아카이브한다. 현재 시스템은 계약을 살려두는 대가로 동기화 노동이 생긴 것.

판정: dryforge 우위 유지 — "자동 vs 수동"에서 "자동 vs 반자동(권고)"으로 격차 축소.

07 진입 단순성 dryforge 우위— 유지▶

판정 불변: dryforge 우위. 설치 = 플러그인 명령 2줄, 사용 = 명령 3개(/ready → /go, 기존 코드는 /migration 1회), 입력 = "아무거나, 혹은 아무것도"(한 줄 아이디어·외부 스펙·잡메모 전부 수용). 학습할 시퀀스가 없다.

현재 시스템: 템플릿 폴더 복사 + reset 스크립트 + 전역 스킬 12종 설치(install-skills.sh + 공개 스킬 출처 2곳) + README의 단계 시퀀스 학습(Phase 1 다섯 스킬의 순서와 이유, 모드 A/B/C 구분, Codex 자연어 트리거 차이). 사용자가 운전자인 설계의 필연 비용이다 — 제어 세분성(축8)과 정확히 맞교환 관계.

참고: 이 축은 "승철님 본인"에게는 이미 매몰비용(학습 완료)이라 체감 격차가 없지만, 새 머신·새 사용자에게 시스템을 옮길 때 실재하는 비용이다(전역 스킬이 폴더 복사로 안 따라오는 함정 포함).

08 제어 세분성 · 모델 혼용 현재 우위— 유지▶

판정 불변: 현재 압승 축. 단계가 스킬 단위로 분리돼 있어 어느 단계든 단독 실행·재실행·중간 개입이 가능하고, 산출물이 전부 영속 파일이라 단계 사이에서 모델을 갈아끼울 수 있다. Claude(기획 강점)+GPT(대량 구현 강점) 분업이 설계 전제이고 /handoff가 그 교환점. Codex의 자연어 트리거까지 규약화돼 있다.

dryforge: ready→go가 한 세션 연속 파이프라인(3-doc이 권위라 세션 단절은 견디지만, 설계상 개입점은 G7과 종료 승인 2개). Claude/Codex 패리티(같은 스킬이 양쪽에서 동작)는 있지만 혼용(단계별로 다른 모델) 시나리오는 설계에 없다. 중간에 "이슈만 다시 자르고 싶다", "계약만 고치고 싶다" 같은 부분 재실행 단위가 없다.

의미: 이 축은 취향이 아니라 비용 구조다 — 모델별 강점·요금이 다른 현실에서 단계별 모델 선택권은 직접적인 품질/비용 레버다.

09 리뷰 독립성 dryforge 우위 (근소)▼ 격차 축소 — 이식①④▶

1차 판정: dryforge 우위 (구조적). A=A(자기 작업을 자기가 판정) 회피가 시스템 전반에 깔려 있다 — 기획 2회(intent-completeness가 대화를 재독해 "추측이 grounded로 둔갑한 슬롯" 사냥 + 3-doc-gate가 대화 안 본 채 산출물만 검문), 구현 다층(머지게이트의 선언 표면 대조 — 자기보고 무효, RISKY worktree 격리 구현, 전 변경 대상 final review, 조건부 spec-review, 하네스 리뷰).

무엇이 바뀌었나: 이식①의 의도-감사(기획, 동결 전 1회)와 이식④의 RISKY 마감리뷰(구현, green 후 전진 전 1회)가 들어와 양 Phase 모두 비저자 검문점이 생겼다. 특히 "요약이 아니라 raw diff를 준다(앵커링 방지)", "발견은 게이트 판정을 막지 않는다(게이트가 유일한 done 권위)"는 변형은 dryforge 사상을 현재 철학에 맞게 흡수한 좋은 번안.

그래도 dryforge가 앞서는 이유: 검문 커버리지 — dryforge는 모든 변경이 최소 1회 독립 리뷰(final review)를 거치지만, 현재는 MECHANICAL/NONE goal이 기계 게이트만 통과한다(게이트가 못 보는 proxy-gap은 RISKY에만 보험이 있다). 단, 현재의 기계 게이트는 앵커링이 원천 불가능한 "가장 독립적인 리뷰어"라는 반론도 성립한다 — 종류가 다른 보증이다.

판정: dryforge 우위 유지, 격차는 "체계 부재→커버리지 차이"로 축소.

10 진행 가시화 현재 우위▲ 격차 확대 — 이식②▶

1차 판정: 현재 압승 축. /roadmap이 이슈·active goal·게이트 상태를 읽어 자기완결 HTML 대시보드를 생성 — 2탭(개발로드맵 DAG + 서비스흐름 박스), 3색 상태, ▶ ready 깃발(착수 가능 이슈), 다크/라이트. 생성기 자체가 셀프테스트 5종(deps/ready/shading/service/render)으로 검증되고, README가 "대시보드는 완료의 증명이 아니다 — completion-check를 돌려라"는 워크트리 안전 규칙까지 명시.

무엇이 바뀌었나: 이식②로 의존 정보가 산문("Blocked by")에서 frontmatter depends: 머신 계약으로 격상됐고 대시보드가 이를 우선 파싱한다(충돌 시 frontmatter 승 — 셀프테스트 007 픽스처가 검증). DAG의 정확도 기반이 단단해졌다.

dryforge: tracking/status.md(전체 스코프 대비 현재 위치를 산문으로) + .dryforge/NNN/ 아카이브 넘버링. 비개발자가 "지금 어디까지 왔나"를 한눈에 보는 채널로는 텍스트 파일이 대시보드를 못 이긴다.

판정: 현재 우위 유지·강화. (승철님의 "비개발 vibe-coder용 가시화" 요구에서 가중치가 특히 큰 축.)

11 성숙도 · 검증 이력 현재 우위— 유지▶

판정 불변: 현재 우위. 이 템플릿은 자기 자신으로 실제 산출물을 만들었다 — 로드맵 대시보드 v2→v3가 이 워크플로우의 풀사이클(grill→PRD→spec→issues 5건→goal 5건 변환→ALL_DONE)로 빌드됐고, 그 과정의 부채가 findings 아카이브에 남아 있다. v1.0(dryforge+MECE 정비)→v1.1(리뷰 3라운드: 거짓완료 가드·라우팅·diagnose·글리프·복사위생)→v1.2(이식 6건)의 정비 이력이 커밋 로그로 추적된다. 스크립트는 도그푸딩으로 두들겨 맞은 상태(예: cp949 글리프 오염 사고를 겪고 탐지·복원 규약화).

dryforge: 문서 품질은 의심할 여지없이 높다(설계 원칙의 일관성, 실패모드 — reward-hacking·A=A·앵커링 — 에 대한 자각이 문서 전반에 배어 있음). 다만 공개 검증 이력을 확인할 수 없다 — 클론 HEAD가 단일 커밋(README EDIT)이라 변경 이력 평가가 불가하고, CHANGELOG는 87단어다. 실프로젝트 적용 사례·이슈 트래킹도 본 분석 시점엔 관찰 불가.

한계 고지: 이 판정은 "관찰 가능한 증거" 기준이다. dryforge가 비공개로 충분히 검증됐을 가능성은 배제 못 한다 — 축의 본질은 "검증 이력의 가시성"에 가깝다.

12 기존 코드베이스 온보딩 dryforge 우위— 유지▶

판정 불변: dryforge 압승 축. /migration이 전용 1회 변환을 제공한다 — SCAN(코드·문서·git 이력으로 manifest/ledger 구축)→ELICIT(코드가 증언 못 하는 것만 위험 가중 질문: "auth 체크가 무엇을 하는지"는 코드가 보여주지만 "그게 정책의 전부인지"는 사용자만 안다)→GENERATE(하네스 전체)→비저자 REVIEW(4차원 루브릭: 밀도·형식·완결·코드 교차검증)→사용자 게이트. ledger의 전 항목이 confirmed/asked-answered/N/A-사유로 종결돼야 해 커버리지가 관찰 가능하다.

현재 시스템: 전용 장치 없음. 기존 프로젝트에 이식하려면 AGENTS.md 2섹션 수기 작성 + CONTEXT.md·ADR을 대화로 소급 구축 + to-spec을 "코드에서 역추출" 용도로 변칙 운용해야 한다 — 가능은 하나 규약이 없다.

의미: 신규 프로젝트 전용 템플릿이라는 정체성의 그림자다. 기존 코드베이스를 자주 받게 되면 이 축의 가중치가 급등한다 — 그 경우의 처방은 §남은 격차의 "온보딩 체크리스트 이식" 또는 "migration만 빌려 쓰기"(dryforge는 1회성이라 혼용 충돌이 없다).

참고축 2개 — 이번에 새로 본 관점 (점수 미합산)

1차와의 비교 가능성을 위해 12축 점수에는 넣지 않고 별도로 기록한다.

⑬ git 안전 · 실패 복구 — dryforge 우위

dryforge: main 직접 쓰기 금지(기존 프로젝트는 feature branch), 시작 전 더티 트리·미푸시 커밋이면 중단, 실패 태스크의 worktree 보존(진단용), 재시도는 bounded ladder(맥락 보강→모델 상향→사용자), 최종 통합(머지/PR)은 절대 자율로 안 함.
현재: 현재 브랜치에 직접 커밋 + iteration 끝 푸시. 대신 red/green/refactor 단위의 잘게 쪼개진 커밋 규율이 복구 가능성을 높이고, 게이트 불변 원칙이 "게이트를 고쳐서 통과" 류 오염을 막는다. 솔로 환경에선 충분하나, 보호 수준 자체는 dryforge가 높다.

⑭ 스코프 규율 (scope creep 방지) — 무승부

현재: "범위 밖이면 고치지 말고 기록" invariant + goal의 forbidden-actions + cycle의 out-of-scope 명시 + findings 큐 — 수명주기형 규율(발견을 잃지 않고 다음 사이클로). 단 goal 경계가 모호하면 무력화된다는 자기 인식도 문서화돼 있음.
dryforge: 머지게이트가 "diff가 선언된 작업 표면을 건드렸는가"를 기계로 대조 + 범위 밖 발견은 findings.md에 기록 후 연기(scope-limited delta) — 태스크 단위 기계 검문. 접근이 다를 뿐 둘 다 실효적.

남은 격차의 성격 — "베낄 산문은 소진됐고, 엔진이 남았다"

dryforge 우위 6축의 나머지 격차를 "이식 가능성"으로 분해했다. v1.3 후보와 비이식 권고.

종합 판정

① 정량 — 12축 6 : 6 (1차와 동일). 단 축 내부가 움직였다: dryforge 우위 6축 중 3축(01 기획깊이 · 06 동기화 · 09 리뷰독립)이 이식으로 "근소" 격차로 전환, 현재 우위 6축 중 4축(02 계약영속 · 03 토큰 · 05 무인 · 10 가시화)은 이식·정비로 더 단단해졌다. 같은 6:6이 아니다 — 기울기가 현재 쪽으로 이동한 6:6이다.

② 정성 — 이식 프로그램은 완료됐다. 남은 dryforge 우위(병렬 엔진, 일체형 진입, migration)는 산문 이식이 불가능하거나(엔진), 이식하면 현재 시스템의 우위 축을 파괴하는(일체형) 것들이다. v1.3에서 가져올 만한 것은 §남은 격차의 P2 산문 4건 정도가 전부 — 그 이후 dryforge는 "경쟁 상대"가 아니라 특정 상황에 빌려 쓰는 연장으로 보는 게 정확하다.

③ 맥락 가중 판정 — 현재 시스템이 백본. 승철님의 실사용 프로파일에 12축을 가중하면: 비개발 솔로(→가시화·진입의 학습은 매몰완료) · Claude 기획+GPT 구현 분업(→축8이 전제조건) · 야간 무인 사이클(→축5가 전제조건, dryforge는 구조적으로 불가) · 살아있는 계약 위에 장기 반복(→축2) · 토큰 직접 부담(→축3). dryforge 우위 축 중 사용 맥락에서 상시 체감되는 것은 사실상 없다(병렬·온보딩·진입은 모두 간헐 상황).

④ dryforge를 그대로 쓰는 게 나은 경우 — (a) 템플릿 자산 없는 새 환경/타인에게 워크플로우를 즉시 줘야 할 때(플러그인 2줄), (b) 기존 코드베이스의 1회 온보딩(/migration만 빌려 쓰기 — 1회성이라 현 체계와 충돌 없음), (c) 독립 태스크 다발 + 마감이 급해 벽시계가 귀할 때, (d) 비한국어 협업자와 같은 레포에서 일할 때(사용자 언어 자동 추적).
