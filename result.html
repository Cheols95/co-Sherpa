현재 워크플로우 — "조립형 스킬 + 영속 게이트 하네스" dryforge — "2-커맨드 일체형 파이프라인"

한 줄 결론 — 전면 우위는 없다. 12개 축에서 6 : 6. 단, 승철님의 사용 맥락에서는 현재 시스템이 백본(등뼈)으로 우위

두 시스템은 같은 문제("AI 에이전트가 멋대로 결정하고, 결정이 휘발되는 것")를 다른 지점에서 푼다. dryforge는 코드를 쓰기 전(기획 단계의 빈틈 열거·강제 질문)에 가장 강하고, 현재 워크플로우는 코드를 쓴 후(영속 기계 게이트로 회귀를 영구 감시, 부채를 무인 루프로 소진)에 가장 강하다. 토큰 비용은 사이클당 현재 시스템이 약 4~6배 저렴(추정), 병렬 처리량(wall-clock)은 dryforge가 우위.

권고: 현재 시스템을 유지하되, dryforge에서 검증된 5가지 장치(결정표면 열거, 의존성 그래프, 사이클-말 문서동기화 후크, 독립 리뷰, 런타임 스모크)를 이식한다. → 「판정 & 권고」 탭

두 시스템의 철학 차이 — 한눈에

현재 워크플로우

"검증을 코드(bash)로 영속화한다"

  • 형태: 12개의 독립 스킬을 사용자가 단계별로 조립 — 라이브러리 방식
  • 핵심 자산: goals/*.gates.sh = 한 번 만들면 영구히 도는 기계 검증 게이트 (게이트: "완료"의 정의를 셸 스크립트로 박제한 불변 계약)
  • 완료 판정: LLM의 자기 보고가 아니라 bash 실행 결과(exit code) — 토큰 0원
  • 부채: findings 큐 → cycles 묶음 → 무인 야간 루프로 소진
  • 사람의 역할: 지휘자 — 각 스킬 호출 시점과 순서를 직접 결정
dryforge

"결정을 코드 작성 전에 전부 캐낸다"

  • 형태: /ready → /go 2개 커맨드의 일체형 파이프라인 + /migration(기존 코드 1회 온보딩)
  • 핵심 자산: 3-doc 계약(handoff·spec·plan) + 프로젝트 harness (harness: CLAUDE.md/AGENTS.md + docs/ 8종 — 세션이 죽어도 살아남는 프로젝트 기억)
  • 완료 판정: 검증 명령 exit 0 캡처 + 런타임 스모크 + 비저자 리뷰 — 단, 그 사이클 안에서만
  • 부채: findings.md 기록 후 다음 /ready 사이클로 이월(소진 루프 없음)
  • 사람의 역할: 승인자 — 질문에 답하고 2개 관문에서 승인만
본질 요약: dryforge는 "기능 1개를 정확히 뽑는 사이클"을 최적화한 도구이고, 현재 워크플로우는 "프로젝트 수명 전체(여러 사이클 + 회귀 + 부채 + 문서 노화)"를 최적화한 하네스다. 경쟁 관계라기보다 최적화 구간이 다르다 — 그래서 부분 이식이 정답이 된다.

현재 워크플로우 — 3계층 구조

계층 1 · 기획 스킬(전역, Matt Pocock + bespoke): grill-with-docs(인터뷰로 용어·결정 벼리기 → CONTEXT.md/ADR) → prototype(스파이크) → to-prd(PRD) → to-spec(계약 고정 — data-schema·api-contract·domain-types를 docs/spec/에 0→1 생성, 자체 제작) → to-issues(수직 슬라이스 이슈) → handoff(모델 전환 인계).

계층 2 · FCG 구현 하네스(greatsumini cc-system): fcg-goal이 단일 엔진으로 3개 모드를 자동 판별 — B 변환(이슈/PRD → goal 3파일 계약: .md 미션 + .gates.sh 기계검증 + .next-task.sh 힌트), A 게이트 루프(TDD RED→GREEN→REFACTOR로 active goal을 green화, green이면 자동 전진), C 사이클 실행(cycle 문서를 받아 findings 소진까지 무인 루프, 3회 무진전 시 blockers.md 기록·조기종료 금지). 보조로 fcg-findings(범위 밖 발견 큐잉)·fcg-cycles(findings를 한 세션 작업서로 묶기).

계층 3 · 정비(Phase 2.5): spec-sync(계약↔코드↔ADR 드리프트 정합, 자체 제작) · improve-codebase-architecture(얕은 모듈 발굴→finding 큐잉) · /roadmap(이슈·게이트·서비스흐름 HTML 대시보드).

토대: bash 오케스트레이터 7종(diagnose / active-check / completion-check / check-gate-rigor / next-task / update-state / _gate-cache) — 게이트 병렬 실행·캐시·rigor 메타검증("every X"를 주장하면 게이트가 X를 열거하는지 검사)을 LLM 토큰 없이 수행.

dryforge — 3개 스킬, 31개 레퍼런스 문서의 일체형 설계

/ready (기획·계약): 어떤 입력이든(한 줄 아이디어~타 도구가 뱉은 장문 문서) "도전 가능한 재료"로 강등하고 7단계를 돈다 — ORIENT(코드·하네스 접지) → DECOMPOSE(입력 해체, 출처 간 충돌은 해소 않고 플래그만) → ELICIT(심장부: 엔티티마다 4개 렌즈(구조/행위/기술/계약)로 설계가 답해야 할 결정을 전부 열거하고, 각 결정을 "사용자 의도에서 도출됨" 또는 "질문함" 둘 중 하나의 종착 상태로 강제 — 조용한 기본값 채택은 종착 상태가 아님) → intent-completeness(비저자 서브에이전트가 "제작자의 몰래 추측"을 사냥) → SPEC+충실도리뷰 → PLAN(태스크 계약 + 의존성 DAG를 YAML로) → HANDOFF → 3-doc-gate(대화를 못 본 서브에이전트가 산출물만 보고 실행가능성 감사) → 사용자 승인(G7).

/go (실행): DAG를 위상정렬해 wave(파동) 단위 실행. 병렬 wave는 git worktree(작업 사본 폴더)로 격리해 ≤8 동시 구현 → merge-gate(브랜치가 실제 전진했고 diff가 선언된 파일만 건드렸는지 — 자기 보고는 증거로 안 침) → 통합 게이트(머지 결과에 검증 명령 실행, exit 0 캡처) → 완료 게이트 + 런타임 스모크(서비스 스펙이면 부팅해 실제 요청 1회) → harness 생성/delta 갱신 → 비저자 final review → 사용자 승인 → 3-doc 아카이브. 리스크 등급(RISKY/MECHANICAL/NONE)으로 검증 강도를 차등.

/migration (1회 온보딩): 기존 코드베이스를 SCAN→ELICIT(코드가 증언 못 하는 것 — 도메인 불변식·보안 경계·비즈니스 모델 — 만 위험가중 질문)→harness 생성→비저자 리뷰→승인.

설계 사상: "Floor, not ceiling"(절차는 바닥만 고정, 결론은 모델에 위임 — 모델이 좋아지면 결과도 좋아짐) · "Ask, don't guess" · 보고는 결과만(과정 내레이션 금지 = 출력 토큰 절약) · 사용자 언어로 비전문가 어휘 출력 · 산출 문서에 dryforge 어휘 0(락인 없음).

생애주기 단계별 대응 관계

기획 → 계약 → 분할 → 구현 → 검증 → 유지관리의 각 단계에서 두 시스템이 무엇으로 답하는지.

단계현재 워크플로우dryforge
아이디어 구체화 /grill-with-docs — 1문1답 인터뷰, 용어를 CONTEXT.md에, 결정을 ADR로 즉시 기록. 필요시 /prototype 스파이크강도는 모델·사용자 재량. AGENTS.md의 "Phase 1 elicitation 게이트"가 load-bearing 선택의 침묵-기본값을 금지(v1.1에서 보강) /ready ELICIT — 엔티티×4렌즈로 결정표면을 강제 열거, 미접지 결정은 전부 질문/도출로 종결. 첫 사이클이면 도메인 모델·스택 설계 대화를 추가 강제"열거는 빠짐없이, 질문은 최소로"(파생 가능하면 안 물음, 질문엔 추천안 선행)
요구 문서화 /to-prd → docs/prd/PRD.md (유저스토리 장대 목록 + 구현·테스트 결정) /ready SPEC → .dryforge/spec.md (행위 규칙·불변식·엣지의 명시 처분·검증 요구)
계약 고정 /to-spec → docs/spec/ + INDEX.md — PRD·ADR보다 우선하는 단일 진실원천. 품질 floor(검증가능·반례·메커니즘·엣지 구체화) 강제, 미결정은 TODO로 정직하게 노출 spec.md가 그 사이클의 ground truth. 사이클 종료 시 아카이브되고, 살아있는 계약 역할은 harness 문서(contracts.md·business-rules.md)로 이관
작업 분할 /to-issues — 수직 슬라이스(tracer bullet) 이슈 "목록", Blocked-by는 산문 /ready PLAN — 태스크별 행위 계약 + 기계가독 의존성 DAG(YAML: depends/regen_barriers/risk)
인계/경계 /handoff 문서로 모델 전환(Claude→Codex). 경계에서 /fcg-goal 모드B가 이슈→goal 3파일 실행계약으로 변환 1회 변환 단계 없음 — plan이 이미 실행계약. ready→go는 같은 세션(컨텍스트 연속), 단 권위는 대화가 아닌 3-doc
구현 /fcg-goal 모드A — 단일 에이전트 직렬 TDD 루프(RED→GREEN→REFACTOR 커밋 규율), 게이트 green이면 자동 다음 goal. 병렬은 /branch 세션 복제로 수동 /go — DAG 기반 병렬 wave(워크트리 ≤8), 리스크 차등 검증(test-first where it fits), merge-gate·통합 게이트·완료 게이트·런타임 스모크
완료 판정 .gates.sh exit 0 — 영속(이후 어느 시점이든 재실행하면 회귀 검출). 거짓완료 가드 + check-gate-rigor 메타검증 검증 명령 exit 0 캡처 + 스모크 + 비저자 리뷰 — 그 사이클 1회성. 이후 회귀 감시는 프로젝트 자체 테스트의 몫
리뷰 사람 리뷰 → 통찰을 finding으로 큐잉(리뷰=소통·학습, 검증은 게이트 몫). 독립 AI 리뷰는 워크플로우 외부(/code-review 등) 비저자 서브에이전트 리뷰가 파이프라인에 내장 — ready 2회(intent-completeness·3-doc-gate), go 1회+(final review, 조건부 spec-review)
부채 관리 /fcg-findings(file:line 증거 강제, 정직성 규칙) → /fcg-cycles(우선순위·의존성으로 묶기) → 모드C 무인 야간 소진 docs/tracking/findings.md에 기록·이월. 소진은 다음 /ready 사이클(사람 개시) — 전용 배치 루프 없음
문서-코드 동기화 /spec-sync — 사용자가 주기적으로 호출. 문서 드리프트는 직접 정합, 코드 수정 필요분은 finding 큐잉 /go 9단계가 매 사이클 자동 — harness를 양방향 delta 갱신(이번 변경이 기존 서술을 무효화했는지도 검사), 스코프 밖 불일치는 findings.md로
아키텍처 정비 /improve-codebase-architecture — deepening 후보 발굴 → finding → cycle → goal 파이프라인 전용 장치 없음(모델 판단과 리뷰에 위임)
현황 가시화 /roadmap — 이슈·게이트 3색·▶active·서비스흐름 2탭 HTML 대시보드 + self-test 5종 docs/tracking/status.md — 전체 스코프 대비 위치를 텍스트로
기존 코드 온보딩 없음(신규 프로젝트 템플릿 복제가 전제) /migration — 위험가중 질문으로 코드가 말 못 하는 정책을 캐내 harness 생성

단어수는 실측(공백 분리). dryforge 레퍼런스는 스테이지 진입 시 강제 로드(force-load)되므로 대부분 실제 컨텍스트 비용이 된다.

구조적 관찰: 현재 시스템에서 "없음"인 것(독립 리뷰 내장, DAG 병렬, 자동 문서동기화, 온보딩)은 대부분 장치를 추가하면 되는 것이고, dryforge에서 "없음"인 것(영속 게이트, 부채 소진 루프, 대시보드, 아키텍처 발굴)은 대부분 설계 철학상 자리가 없는 것(사이클 단위 세계관)이다. 이식 방향이 dryforge→현재 쪽으로 자연스러운 이유.

토큰 효율 — 인스트럭션 로드 실측 기반 추정

기준: 각 스킬이 강제 로드하는 인스트럭션(스킬 본문+레퍼런스)의 실측 단어수 → 토큰 환산(영문 ≈1.3 tok/단어, 국문 혼합 ≈1.8~2.2 tok/단어). 대화·코드·산출물 토큰은 양쪽 모두 제외(공통 비용). ±표시된 모든 수치는 추정치이며 실 계측이 아니다(⑧ 탭 참조).

생성물 의존 (수천 단어 규모)

dryforge harness는 "밀도가 목적"(hollow 문서 금지)이라 잘 쓰이면 재설명 비용을 크게 줄인다 — 기저 부하 증가와 세션 간 기억의 트레이드. 현재 시스템은 같은 역할을 docs/spec/INDEX 우선 읽기 순서(필요분만 로드)로 푼다.

판정: 사이클당 인스트럭션·디스패치 비용은 현재 시스템이 약 4~6배 저렴(본세션 기준, 서브에이전트 포함 시 격차 더 벌어짐). dryforge의 비용은 낭비가 아니라 의도된 선불(엘리시테이션·독립검증·병렬화에 투자해 재작업을 없앰)이다 — README 스스로 "front-loads cost"라 명시. 따라서 올바른 질문은 "누가 싸냐"가 아니라 "그 선불이 회수되는 프로젝트인가"다: 요구가 모호하고 재작업 위험이 큰 신규 기능 → 회수됨. 요구가 이미 또렷하고(현재 템플릿의 Phase 1 산출물처럼) 사이클이 잦은 장기 프로젝트 → 매 사이클 ~40k tok의 고정 세리머니가 부담. 참고로 dryforge의 "결과만 보고(과정 내레이션 금지)" 규율은 출력 토큰을 실제로 아끼는 좋은 장치 — 이건 비용이 아니라 절감 항목.

12개 축 심층 분석

각 항목을 펼치면 근거가 나온다. 배지 = 우위 판정.

dryforge 우위 1. 기획 엘리시테이션 깊이 ▶

dryforge ELICIT는 "물어볼 것을 생각해내는" 게 아니라 설계가 답해야 할 결정의 전수 목록을 먼저 만들고(엔티티 명세 → 구조/행위/기술/계약 4렌즈 × 엔티티·충돌쌍) 각 결정을 ①사용자 의도에서 도출 ②질문 둘 중 하나로만 종결시킨다. "조용한 기본값"은 종결 상태가 아니다. 그 위에 비저자 감사 2중(intent-completeness가 대화를 읽고 제작자의 몰래 추측을 사냥, 3-doc-gate가 대화를 못 본 채 산출물만 감사). "다운스트림 게이트를 믿고 윗단을 얕게 하는 것은 reward-hacking"이라고 명시적으로 금지하는 등 LLM 실패 모드를 정조준한 문구가 인상적.

현재의 grill-with-docs는 1문1답·코드 대조·시나리오 스트레스 테스트로 방향은 같지만, 완결성을 보장하는 열거 장치가 없다 — README가 직접 "grill에만 의존하지 말고 7항목을 확인하라"고 사용자에게 경고할 정도. v1.1에서 AGENTS.md에 "Phase 1 elicitation 게이트"(load-bearing 선택의 침묵-기본값 금지, 평어 질문→정밀 규칙 번역)를 넣어 일부를 흡수했지만, 구조적 열거+독립 감사는 아직 없다. 이식 1순위.

현재 우위 2. 계약의 영속성·회귀 감시 ▶

FCG의 .gates.sh는 사이클이 끝나도 영구히 남는 기계 검증 계약이다. 6개월 뒤 어떤 변경이 goal 3의 불변식을 깨면 completion-check.sh(전 게이트 병렬 스윕)가 잡아낸다. 게이트 불변 원칙(코드를 고치지 게이트를 고치지 않는다) + check-gate-rigor.sh(메타검증: "every X" 주장 ↔ 열거 게이트 일치) + 거짓완료 가드까지, "완료 선언"을 LLM의 자기보고에서 분리하는 장치가 겹겹이다.

dryforge의 검증은 강력하지만 그 /go 런 안에서만 존재한다. 사이클이 끝나면 spec은 아카이브되고, 이후 회귀 감시는 프로젝트의 일반 테스트 스위트 몫. "spec이 코드와 다르면 spec이 이긴다"는 권위 규칙은 harness 산문에 남지만, 산문은 기계가 강제하지 못한다. 장기 프로젝트일수록 이 차이가 누적된다.

현재 우위 3. 토큰 효율 ▶

⑤ 탭 상세. 사이클당 본세션 인스트럭션 ~7-8k vs ~38-42k tok(추정), 서브에이전트 디스패치 0 vs N+3회, 검증 비용 토큰 0(bash) vs 리뷰 토큰. 현재 시스템의 README 운영 팁(병렬은 /branch로 세션 복제 — "토큰 효율적")까지 포함해 일관되게 토큰-보수적 설계.

dryforge 우위 4. 병렬 처리량 (wall-clock) ▶

dryforge /go는 DAG 위상정렬 → 독립 태스크를 git worktree로 격리해 ≤8 동시 구현, 워크트리 풀 재활용, 게이트와 다음 wave 프로비저닝 오버랩, 의존성 공유(심링크) 등 병렬 실행 공학이 정교하다. merge-gate가 "브랜치가 실제 전진 + diff가 선언 표면만"을 기계 확인해 병렬의 위험(자기보고·표면 이탈)을 차단.

현재는 단일 에이전트 직렬이 기본. goal 스택 자체가 "가장 낮은 실패 goal = active" 단선 구조라 병렬 실행 개념이 없고, 병렬은 /branch 수동 운용. 처리량이 중요한 대형 슬라이스 묶음에서는 명백히 dryforge가 빠르다(토큰↑ ↔ 시간↓ 트레이드).

현재 우위 5. 부채 관리·무인 운영 ▶

FCG의 차별 자산: finding은 frontmatter(resolved/priority/related)와 file:line 증거 강제("못 짚으면 hunch"), 종결 시 코드 대조 검증·증거 인용이라는 정직성 규칙을 가진 1급 문서다. 쌓이면 /fcg-cycles가 우선순위·의존성으로 묶어 야간 무인 루프(조기종료 금지, 3회 무진전 시 blockers 기록 후 다음 타깃)로 소진한다. "자는 동안 부채가 줄어드는" 운영이 시스템으로 성립.

dryforge는 findings.md에 기록·이월하고 에스컬레이션이 동기식(사용자 답변까지 런 정지)이라 설계상 유인(attended) 운영이다 — 정확성엔 좋지만 무인 배치는 불가.

dryforge 우위 6. 문서-코드 동기화 자동성 ▶

dryforge는 /go 9단계에서 매 사이클 harness를 delta 갱신한다 — 그 전에 3-doc을 재독(세션이 코드 편향된 상태를 교정)하고, 양방향(이번 변경이 기존 서술을 무효화했는지)으로 정합하며, 스코프 밖 불일치는 findings로 이월. 문서 노화가 구조적으로 억제된다.

현재 spec-sync는 분류 규칙(직접 갱신/finding/질문)이 잘 다듬어져 있지만 사용자가 기억해서 돌려야 한다 — README 스스로 "의식적으로 할 필요"라고 쓴 약점. 단, 동기화 대상의 권위는 현재 쪽이 강하다(docs/spec은 기계가 우선 참조하는 단일 진실원천, harness는 산문 기억). 자동 트리거만 이식하면 되는 축.

dryforge 우위 7. 진입 단순성 ▶

커맨드 2개·승인 2회·질문엔 추천안 선행(1키 수락)·비전문가 어휘 출력·플러그인 마켓플레이스 설치. 비개발자 바이브코더의 인지 부하가 확연히 낮다. 현재 시스템은 스킬 12개의 호출 시점·순서를 사용자가 알아야 하고(README 워크플로우 표가 그 증거), Codex 쪽은 자연어 트리거 규약까지 숙지해야 한다. 숙련된 운영자(승철님)에게는 비용이 아니지만, 전파·온보딩에는 불리.

현재 우위 8. 제어 세분성·모델 혼용 ▶

현재는 단계가 모두 분리돼 있어 "오늘은 grill만", "spec만 다시", "이 cycle만 야간 실행" 같은 부분 구동이 자유롭고, Claude(기획)/GPT(구현) 역할 분업이 handoff로 공식 지원된다(구독 토큰 예산 분산 효과 포함). dryforge는 ready→go가 한 세션 한 모델의 일체형이라 중간 개입 지점이 G7과 동기 에스컬레이션뿐이고, 플랫폼은 양쪽 지원하되 한 런은 한 모델이다.

dryforge 우위 9. 리뷰 독립성 ▶

"자기 산출물을 자기가 판정하는 것(A=A)이 가장 약하다"는 원칙이 시스템 전반에 박혀 있고, 비저자 서브에이전트 검증이 ready 2회·go 1회+로 파이프라인에 내장돼 있다. 리뷰어에게 구현자의 요약이 아닌 raw diff를 주는 것(앵커링 방지), 리스크 비례 검증, "평가 불능 검사는 실패로 친다" 같은 디테일이 좋다. 현재 시스템의 독립 검증은 게이트(기계)가 맡고 AI 리뷰는 외부 도구(/code-review) 호출에 의존 — goal 닫기 전 독립 리뷰가 규약에 없다.

현재 우위 10. 진행 가시화 ▶

/roadmap 대시보드(이슈·게이트 3색·▶active 깃발·개발로드맵 DAG + 서비스흐름 2탭, 다크/라이트, self-test 5종)는 비개발자가 "지금 어디까지 왔나"를 보는 데 특화된 자산으로, dryforge의 status.md 텍스트와 체급이 다르다. 특히 비개발 이해관계자 공유용으로 유효.

현재 우위 11. 성숙도·검증 이력 ▶

현재 시스템: 출처 3곳(Matt Pocock·cc-system·자체 제작)의 검증된 부품 + 승철님이 실제 프로젝트(roadmap 대시보드 v2→v3)로 풀사이클 검증 + 3라운드 자체 리뷰 정비(거짓완료 가드·라우팅·복사위생 등) 완료. dryforge: 첫 릴리스 2026-06-01, v1.1.0이 06-09 — 출시 1주차에 9개 릴리스(빠른 개선은 장점이자 불안정 신호). 카카오 오픈채팅(~2천명) 바이럴은 사용성 방증이지만 장기 프로젝트에서의 검증 사례는 아직 없다. 다만 코드 품질 자체는 1주차답지 않게 치밀하다(실패 모드 명시, git 안전 규칙, 플랫폼 패리티 빌드).

dryforge 우위 12. 기존 코드베이스 온보딩 ▶

/migration은 "코드가 보여주는 것(auth 체크가 뭘 하는지)과 코드가 증언 못 하는 것(그게 정책의 전부인지)"을 구분해 후자만 위험가중으로 질문하고 harness를 1회 생성한다. 현재 템플릿은 신규 프로젝트 복제 전제라 이 시나리오가 비어 있다 — 기존 프로젝트에 FCG를 얹으려면 수작업.

종합 판정

① 절대 평가: 무승부(6:6), 최적화 구간이 다르다. dryforge는 "기능 1개 사이클"(요구 모호 → 정확한 산출)의 완성도가 높고, 현재 시스템은 "프로젝트 수명 전체"(여러 사이클·회귀·부채·문서 노화·무인 운영)의 완성도가 높다.

② 맥락 평가(승철님 기준): 현재 시스템이 백본으로 우위. 근거 —

  • 템플릿 복제 기반 신규·장기 프로젝트 운영: dryforge의 강점인 /migration이 불필요하고, 현재의 강점인 영속 게이트·부채 루프가 직격으로 유효
  • Claude 기획 / GPT 구현 분업이 이미 자리잡음: dryforge 일체형은 이 운영 모델과 충돌
  • 토큰 예산 의식: 사이클당 4~6배 격차는 사이클이 잦을수록 복리로 벌어짐
  • 무인 야간 운영·roadmap 대시보드 등 이미 체화된 자산을 dryforge는 대체 못 함

③ 단, dryforge가 명백히 나은 4개 축(엘리시테이션·병렬·자동 동기화·독립 리뷰)은 실재하는 격차다. 아래 이식안으로 흡수하는 것이 "갈아타기"보다 이득이 크고 위험이 작다.

권고 — dryforge에서 이식할 5가지 (우선순위순)

  1. 결정표면 열거 + 독립 의도-감사 (기획 게이트 강화) — grill-with-docs 종료 조건 또는 to-spec 전 단계에 "엔티티 명세 → 구조/행위/기술/계약 4렌즈로 미결정 슬롯 열거 → 전부 도출/질문으로 종결" 체크를 넣고, to-spec 직전에 대화를 읽는 비저자 서브에이전트 1회(intent-completeness 상당)로 몰래 추측을 사냥. 기존 AGENTS.md 'Phase 1 elicitation' 게이트의 구조화 완성판. 비용: 서브에이전트 1회/기능. 효과: to-spec의 TODO(미결정) 누락 — 가장 비싼 실패 — 차단.
  2. to-issues에 기계가독 의존성 그래프 — 산문 "Blocked by"를 dryforge처럼 YAML depends 블록으로 병기. 즉시 효용 둘: roadmap 대시보드 deps 렌더의 공급원이 정식 계약이 되고, /branch 병렬 세션에 "무엇이 진짜 독립인가"의 근거 데이터가 생긴다. 장기적으로 fcg-goal 병렬 wave 실험의 토대.
  3. 사이클-말 문서 동기화 후크 — fcg-goal 모드C 종료 절차와 completion-check ALL_DONE 시점에 "spec-sync 실행 권고"를 명시(또는 diagnose.sh가 마지막 spec-sync 이후 커밋 수를 세어 경고). dryforge의 '매 사이클 delta 갱신' 효과를 수동 호출 부담 없이 흡수.
  4. goal 닫기 전 독립 리뷰 옵션 — RISKY한 goal(스키마·결제·보안 등)에 한해 merge/green 선언 전 비저자 서브에이전트가 raw diff vs goal.md 미션을 대조(구현자 요약 금지 — 앵커링 방지). 거짓완료 가드의 의미론 버전.
  5. 런타임 스모크의 게이트 표준화 — "서비스 스펙이면 부팅+요청 1회 2xx"를 _meta deep gate 패턴(DEEP_LABELS_RE)으로 템플릿에 표준 탑재. 이미 finding으로 OPEN인 'UI 렌더 검증(헤드리스)' 항목과 같은 계열 — dryforge는 이를 완료 게이트 필수로 박았다("compiles와 works는 다른 주장").

보너스: dryforge의 출력 규율("결과만 보고, 과정 내레이션 금지·내부 용어 비노출")은 Codex fcg 스킬에 한 단락 추가로 이식 가능한 토큰 절감책이다.

언제 dryforge를 그대로 쓰는 게 나은가

  • FCG 템플릿이 안 깔린 기존 코드베이스에 빠르게 규율을 얹어야 할 때 (/migration)
  • 요구가 매우 모호한 1회성 신규 기능을 한 세션에 정확히 뽑고 싶을 때 (엘리시테이션 선불이 즉시 회수)
  • 독립 태스크가 많은 대형 슬라이스를 시간 우선(토큰 불문)으로 처리할 때 (병렬 wave)
  • 워크플로우를 모르는 협업자/비개발자에게 에이전트 운영을 맡길 때 (커맨드 2개)

두 시스템은 같은 레포에서 공존 가능하다(겹치는 파일 규약 없음 — dryforge는 .dryforge/와 docs/ 8종, 현재는 docs/spec·goals·cycles). 단 진실원천이 2벌이 되므로(spec vs harness) 상시 병용은 비권장 — 실험은 별도 프로젝트에서.

방법론

  • dryforge: github.com/fn-opt/dryforge를 임시폴더에 클론(%TEMP%\dryforge, HEAD=d9c2bde, v1.1.0/2026-06-09). 단일 소스(src/skills/) 31개 md 전수 목록화, 3개 SKILL.md 전문 + 핵심 레퍼런스 4종(orchestration·output-format·dependency-calc·harness-lifecycle) 전문 정독, 나머지는 SKILL.md 내 요약·상호참조로 파악. 파일별 단어수 실측.
  • 현재 워크플로우: 이 레포(README·AGENTS·CLAUDE·docs/fcg-system·goals/AGENTS·guidelines/goal-iteration) + 전역 스킬 12종 SKILL.md(~/.claude/skills/) 전문 정독, 파일별 단어수 실측, bash 오케스트레이터 역할은 문서·기존 운영 이력으로 확인.
  • 토큰 추정: 단어수 실측 × 환산계수(영문 ≈1.3, 국문 혼합 ≈1.8~2.2 tok/단어) + 각 스킬의 force-load 규약을 따라 "한 사이클에 로드되는 인스트럭션"을 합산.

한계 — 읽을 때 유의

  • 토큰 수치는 전부 추정치다. 실 API 계측이 아니라 인스트럭션 텍스트 측정 기반. 대화·코드 컨텍스트·캐시 효과에 따라 실제 격차는 달라질 수 있다(다만 4~6배라는 차수 자체가 뒤집힐 가능성은 낮다 — 서브에이전트 디스패치 구조 차이가 지배적이므로).
  • dryforge를 실제로 구동해 보지 않았다. 소스 분석상 설계는 치밀하나, 엘리시테이션의 체감 품질(질문이 정말 적절한가, 과잉 질문은 없는가)과 병렬 실행의 안정성은 실사용 검증이 필요하다. 본 보고서의 dryforge 평가는 "설계 의도가 문서대로 작동한다"는 가정 위에 있다.
  • 현재 워크플로우 평가에는 운영자 숙련 프리미엄이 들어 있다. "제어 세분성 우위" 등은 시스템을 만든 본인이 운영할 때의 이야기이고, 제3자에게는 학습 비용이 페널티로 작동한다(축 7에서 반영).
  • dryforge는 릴리스 주기가 빠르다(1주 9릴리스). 본 분석은 v1.1.0 스냅샷 기준 — 수 주 뒤에는 격차 항목이 달라질 수 있다.
