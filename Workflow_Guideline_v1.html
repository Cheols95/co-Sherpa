EVERBUILD Workflow Guideline
TEMPLATE v1.3 · GUIDE v1

두 모델, 하나의 하네스.
기획은 깊게, 구현은 기계처럼.

Claude가 기획·계약을 굳히고(Phase 1), GPT/Codex가 기계 검증 게이트를 초록불로 만들 때까지 구현합니다(Phase 2).

이 문서는 템플릿 워크플로우의 공식 사용자 가이드입니다 — 어떤 단계에서 어떤 스킬을 쓰는지, 각 스킬이 왜 그렇게 작동하는지, 템플릿 개선을 기존 프로젝트로 어떻게 전파하는지를 다룹니다.

큰 그림

역할 분담 — 사람 · Claude · GPT

한 번 셋팅하면 모든 프로젝트의 뿌리가 되는 구조입니다. 사람은 결정만 하고, 모델들은 각자 잘하는 단계를 맡습니다.

👤

사람 = 결정

무엇을 만들지, 갈림길에서 어느 쪽인지만 답합니다. 코드 리뷰 대신 기계 검증 게이트가 "완료"를 판정하므로, 비개발자도 품질의 최종 권위를 가질 수 있습니다.

🧭

Claude = 기획 · 계약

Phase 1에서 요구사항을 그릴링으로 다듬고, PRD → 계약문서(spec) → 이슈 순서로 움직이지 않는 진실원천을 먼저 고정합니다. 계약이 먼저, 구현은 그 위에서.

⚙️

GPT/Codex = 구현 루프

Phase 2에서 goal 게이트를 초록불로 만들 때까지 TDD로 자율 반복합니다. 범위 밖 발견은 고치지 않고 finding 큐에 적립 — 밤새 무인 실행도 가능합니다.

핵심 엔진

FCG — findings · cycles · goals

구현 단계를 지탱하는 3가지 자산입니다. 서로 피드백 루프를 이룹니다: 작업 중 발견 → finding 큐 → cycle로 묶음 → 일부는 goal로 승격 → 게이트가 검증.

docs/findings/

Findings — 부채 큐

현재 작업 범위 밖에서 발견한 버그·부채·아이디어를 잃지 않도록 적어두는 메모 큐. "지금 고치지 말고 기록"이 철칙이라 작업이 옆길로 새지 않습니다(scope creep 방지).

cycles/

Cycles — 작업지시서

쌓인 findings를 우선순위·의존성으로 묶은 한 세션 분량의 루프 구동 문서. "이 문서의 내용을 모두 완수할 때까지"라고 건네면 에이전트가 무인으로 소진합니다.

goals/ + .gates.sh

Goals — 실행계약

미션(.md) + 기계 검증 스크립트(.gates.sh) + 다음 작업 힌트(.next-task.sh) 3파일 세트. 게이트 스크립트가 통과해야만 "완료" — 사람 감이 아니라 코드가 판정합니다.

💡
게이트(gate)란? "이 조건이 깨지면 빨간불"을 검사하는 작은 셸 스크립트입니다. 예: "모든 API 엔드포인트에 테스트가 존재한다"를 실제 파일을 순회하며 확인. 한번 초록불이 된 게이트는 영구 불변식으로 남아, 나중 작업이 과거 완성물을 몰래 망가뜨리면 즉시 빨간불이 켜집니다.
단계별 흐름

Phase 0 → 1 → 경계 → 2 → 2.5

각 단계를 눌러 펼치면 산출물·작동 원리·쉬운 풀이가 나옵니다. 스킬의 더 깊은 설명은 ② 스킬 사전 탭에 있습니다.

Phase 0 — 부트스트랩

새 프로젝트 시작

템플릿 폴더를 복사해서 새 프로젝트를 만드는 단계. 5분이면 끝납니다.

1폴더 복사 + 초기화reset-for-new-project.sh▶
절차
  • 템플릿 폴더를 새 프로젝트 경로로 통째 복사
  • bash scripts/reset-for-new-project.sh — 복사로 딸려온 머신-로컬 상태(.state/, 자동생성 state, 이전 사용자 설정)를 비움. git clone으로 받았다면 불필요
  • git init 후 첫 커밋
🏠 쉬운 풀이 — 모델하우스를 통째로 복사한 뒤, 이전 입주자의 짐(임시 상태 파일)만 비우는 단계입니다.
2전역 스킬 설치 (새 머신만)install-skills.sh▶
절차
  • bash scripts/install-skills.sh — 레포 skills/ 백업에서 Claude 13종 + Codex 4종을 전역 설치
  • 스킬은 머신 전역이라 한 번 깔면 이 컴퓨터의 모든 프로젝트가 같이 씁니다
🔧 쉬운 풀이 — 폴더(자산)는 "재료"고 스킬은 "공구"입니다. 공구는 작업장(컴퓨터)에 한 번만 걸어두면 어느 현장에서든 같은 공구를 씁니다. 자세한 설치 채널 구분은 ③ 업데이트 탭 참조.

Phase 1 — 기획 · 계약

Claude슬래시 명령으로 호출

구현이 흔들리지 않도록 계약을 먼저 고정하는 단계. 순서가 곧 설계입니다: 결정표면을 체크리스트로 닫고(grill) → 닫힌 기능을 한 번에 봉인(freeze: PRD·계약·이슈·graph-lint) → 인계(handoff).

1/grill→ docs/grill/checklist.md · CONTEXT.md · docs/adr/▶
무엇을 계획을 도메인 모델·기존 결정과 충돌시키며 다듬는 그릴링(grilling, 집요한 검증 인터뷰) 세션. 결정표면을 docs/grill/checklist.md에 4개 렌즈(구조 / 행위 / 기술 / 계약)로 회계해 슬롯마다 상태를 추적하고, 용어가 굳을 때마다 용어집(CONTEXT.md)과 결정 기록(ADR)을 그 자리에서 갱신합니다.
종료 판정 — 감이 아니라 회계 엔티티를 나열한 뒤 4렌즈로 설계가 반드시 답해야 할 결정들을 전부 열거하고, 각 슬롯이 네 상태 중 하나로 닫힙니다 — [x] 결정 / [~] 보류 / [>] 실험 대기 / [-] 렌즈 해당없음. 빈칸([ ])도 미해결 [>]도 없으면 grill이 "기능 X 닫힘 — /freeze ready"를 선언합니다. 질문은 grounds-gate(어느 슬롯인지 · 왜 기존 재료로 안 풀리는지 · 잘못 추측하면 어떤 대가인지 3요소를 댈 수 있어야 통과)를 거쳐야 사용자에게 도달합니다.
🔥 쉬운 풀이 — 착공 전 깐깐한 건축사와의 인터뷰입니다. 다만 "충분히 물은 느낌"으로 끝내지 않고, 답해야 할 결정을 docs/grill/checklist.md라는 한 장에 적어 칸칸이 채웁니다 — 결정 [x] · 나중에 [~] · 실험으로 답할 것 [>] · 해당없음 [-]. 칸이 전부 닫혀야 "닫힘" 도장을 찍습니다.
2/prototype(선택) 버리는 시제품▶
무엇을 설계를 확정하기 전에 버릴 각오로 만드는 시제품. 데이터 모델·상태 흐름이 궁금하면 터미널 앱으로, 화면이 궁금하면 과감하게 다른 UI 변형 여러 개를 한 화면에서 토글해보며 고릅니다.
실험은 슬롯에 묶인다 프로토타입은 grill 체크리스트의 어떤 [>](실험 대기) 슬롯을 닫는지 명시해야 합니다 — 슬롯이 없으면 프로토타입도 없습니다. 실험이 끝나면 그 슬롯이 [x]로 닫혀 freeze 자격을 갖춥니다.
🧪 쉬운 풀이 — 본 공사 전의 종이 모형. 모형은 버리는 게 정상이고, 모형에서 얻은 "답"만 설계에 들어갑니다. 모형은 반드시 "어느 질문에 답하려고"(어느 [>] 칸) 만드는지를 정해두고 시작합니다.
3/freeze→ PRD · spec · issues · graph-lint (봉인)▶
무엇을 grill로 닫힌 기능 하나를 단 한 번의 호출로 봉인하는 sealed 번들. 이 호출 자체가 유일한 인간 승인점입니다 — 도장 한 번에 PRD·계약·이슈·그래프 검사까지 한꺼번에 굳힙니다.
내부 5단계 (순서대로)
  • ① 2방향 의도감사 — 기획에 참여하지 않은 비저자 서브에이전트가 처분(disposition) + 잔여 항목 열거(residual-enumeration)로 1회 감사. 대화에서 조용히 채워진 추측(아무도 결정한 적 없는데 문서에 들어간 것)을 사냥합니다.
  • ② to-prd — 대화를 docs/prd/PRD.md로 굳힘. PRD는 "원래 의도"의 사진이라 이후 코드가 바뀌어도 다시 쓰지 않고, 현재 상태의 권위는 spec이 가집니다.
  • ③ spec 생성 / 증분확장 — spec이 없으면 to-spec으로 계약문서(데이터 스키마 · API 계약 · 공개 타입 + INDEX.md)를 처음 생성, 이미 있으면 충돌 검사 후 증분 확장. spec은 구현이 최우선으로 참조하는 단일 진실원천이며 충돌 시 PRD·ADR보다 우선합니다.
  • ④ to-issues — PRD+계약을 수직 슬라이스(화면부터 저장소까지 얇게 관통하는 tracer-bullet 동작 단위) 이슈로 자름. 각 이슈 머리에 기계가 읽는 frontmatter depends:(선행 이슈)·risk: RISKY|MECHANICAL|NONE(위험 등급)이 붙습니다.
  • ⑤ graph-lint — scripts/issues-graph-check.sh로 의존성 그래프의 순환(cycle)·끊긴 참조(dangling)를 검사하는 하드 게이트. 통과해야 봉인이 완료됩니다.
sealed — 중간 질문 없음 번들 실행 중에는 사용자에게 되묻지 않습니다. 모든 미결정은 grill 체크리스트에서 이미 닫혀 있어야 합니다 — 예컨대 테스트 이음새(test seam)는 그릴링에서 정해지지, 봉인 중에 다시 묻지 않습니다.
📜 쉬운 풀이 — 계약서 묶음(PRD·계약·이슈)에 도장을 한 번 찍는 순간입니다. 도장을 찍기 직전 제3자(비저자 에이전트)가 "이 조항, 정말 합의하신 건가요?"를 한 번 더 검토하고, 서류끼리 앞뒤가 맞는지(graph-lint) 기계가 확인합니다. 도장은 닫힌 기능에만 — 기능 단위로 찍습니다.
4/handoff→ 인계 문서 (Phase 1 마무리)▶
무엇을 현재 대화를 다른 에이전트(또는 미래의 세션)가 이어받을 수 있는 압축 문서로 만듭니다. 모델 전환(Claude → Codex)이나 긴 세션 교체 전에 항상 실행합니다.
필수 명시 인계 문서에 goals/ 변환 상태(미변환 | 변환완료)를 반드시 적습니다 — 누락하면 다음 에이전트가 이중 변환하거나 빈 goals에 구현 모드를 돌리는 사고가 납니다.
📋 쉬운 풀이 — 교대 근무자의 인수인계 노트. "여기까지 했고, 다음은 이것, 함정은 저것"을 한 장으로.
✅
Phase 1 마감 체크리스트 — 이제 /grill이 이 결정표면을 docs/grill/checklist.md에 4상태([x]/[~]/[>]/[-]) 라이브 체크리스트로 추적하므로, 아래 7개는 사람이 눈으로 한 번 더 보는 백업입니다. (체크는 저장되지 않습니다 — 눈으로 점검하는 용도)

결정된 문서는 성격대로 갈라 둡니다 — 계약(API·스키마·타입)은 docs/spec/, 설계 참고(흐름·화면·아키텍처)는 docs/design/, 결정 이력은 docs/adr/(한 결정 한 파일, append-only).

경계 — 변환

정확히 한 번

Phase 1의 이슈 "목록"을 Phase 2의 goal "실행계약"으로 바꾸는 단 하나의 작업입니다.

★/build docs/issues/*.md→ goals/<n>-* 3파일 실행계약 (모드 B)▶
무엇을 각 수직 슬라이스를 goals/<n>-<이름>.{md, gates.sh, next-task.sh} 3파일 계약으로 변환합니다. 이슈의 risk: 등급도 goal로 운반됩니다. 첫 변환은 교육용 예제 goals/0-example.*을 제거하고 실제 goal로 교체합니다.
⚠ 함정 변환은 경계에서 정확히 한 번 — 기획(Claude)이 handoff 전에 하거나, 구현(Codex)이 handoff 후에 하거나 둘 중 하나입니다. 그래서 handoff 문서에 변환 상태를 반드시 명시합니다. 층위 구분: 이슈 "목록" ≠ goal "3파일 실행계약" ≠ spec "계약 인터페이스".
📑 쉬운 풀이 — 할 일 목록(이슈)을 "검사기가 딸린 계약서"(goal)로 바꾸는 공증 절차입니다. 같은 목록을 두 번 공증하면 서류가 꼬이니 딱 한 번만.

Phase 2 — 구현

GPT / Codex 주력Claude로도 가능 (슬래시 그대로)

게이트를 초록불로 만드는 자율 루프. TDD 규율(RED 테스트 → GREEN 최소코드 → REFACTOR)이 내장되어 있습니다.

⚠️
모델별 호출 방식이 다릅니다. Claude는 슬래시(/build)가 먹지만, Codex는 슬래시가 안 먹습니다 — 자연어로 트리거하세요: "build 돌려줘", "이건 범위 밖이니 finding으로 적어둬", "cycles/<파일>.md 완수까지 작업해줘". Codex에는 구현용 4종(fcg 3종 + handoff)만 설치되어 있습니다.
1bash scripts/diagnose.sh매 세션 시작 — 상태 진단▶
무엇을 현재 active goal(첫 빨간불 게이트), 열린 finding, blocker를 한 화면으로 보여줍니다. spec이 오래 방치되면(기본: spec 마지막 변경 후 20커밋) /spec-sync 권고도 자동 출력됩니다.
🩺 쉬운 풀이 — 출근하자마자 보는 현장 상황판. "오늘 어디부터?"를 사람이 기억할 필요가 없습니다.
2"build 돌려줘"모드 A — active goal을 GREEN으로▶
무엇을 active goal의 게이트를 통과시킬 때까지 TDD로 자율 반복합니다. 커밋도 규율대로: red(id): → green(id): → refactor(id):. 초록불이 되면 다음 goal로 자동 전진합니다.
RISKY 마감 리뷰 위험 등급이 RISKY인 goal은 초록불 후 전진 전에 작성에 관여하지 않은 서브에이전트가 미션 ↔ 실제 코드 변경분(raw diff)을 1회 대조합니다. 발견은 finding 큐로 가고, 게이트 판정 자체는 막지 않습니다(게이트가 유일한 "완료" 권위).
막히면 — 사다리 3회 연속 무진전이면: 맥락 보강 재시도 1회 → 접근 전환 재시도 1회 → 그래도 안 되면 blockers.md에 기록하고 다음 작업으로. 무한 헛바퀴도, 조기 포기도 막는 구조입니다.
🚦 쉬운 풀이 — "검사기 초록불 될 때까지 일하는 기계"를 켜는 명령. 막히면 무작정 반복하는 게 아니라 정해진 사다리(다른 정보로 재시도 → 다른 방법으로 재시도 → 기록 후 이동)를 탑니다.
3"범위 밖이니 finding으로 적어둬"fcg-findings — 부채 큐잉▶
두 경로 자동: 루프 중 에이전트가 범위 밖 버그·부채를 발견하면 고치지 않고 스스로 큐잉(scope creep 방지의 핵심). 수동: 사용자가 대화 중 "이건 나중에"라고 지시. 리뷰 대화에서 나온 통찰도 1급 출처입니다.
전제 조건 goal의 미션·금지사항이 또렷해야 작동합니다 — 경계가 모호하면 에이전트가 곁가지를 그냥 고쳐버려 기록이 남지 않습니다.
🗒️ 쉬운 풀이 — 도배 중에 수도 누수를 발견하면, 도배를 멈추고 배관공이 되는 게 아니라 메모지에 적어 벽에 붙입니다. 도배는 계속됩니다.
4"쌓인 findings 묶어서 cycle 만들어줘"fcg-cycles — 작업지시서 작성▶
무엇을 미해결 findings를 우선순위·의존성으로 묶어 cycles/<날짜>-<번호>-<이름>.md 한 세션짜리 구동 문서로 만듭니다.
📦 쉬운 풀이 — 벽에 붙은 메모지들을 모아 "오늘 밤 작업지시서" 한 장으로 정리하는 일. 다음 단계에서 이 지시서를 통째로 맡깁니다.
5"cycles/….md 완수까지 작업해줘"모드 C — 무인 루프▶
무엇을 cycle 문서를 입력으로 받아 findings를 소진할 때까지 무인 실행합니다. 조기 종료 금지가 규율 — 막히면 사다리를 타고 blocker로 기록한 뒤 다음 대상으로 넘어갈 뿐, 멈추지 않습니다. 모든 대상이 처리되고 게이트 체인이 초록이어야 종료하며, 종료 시 /spec-sync를 권고합니다.
🌙 쉬운 풀이 — 야간 무인 공장 가동. 아침에 출근하면 완료 보고와 "막혀서 넘긴 것" 목록이 기다립니다. 1인 기업의 시간을 두 배로 늘려주는 기능입니다.

Phase 2.5 — 정비

주기적 · cycle 사이

코드와 문서가 썩지 않도록 주기적으로 돌리는 유지보수 단계입니다.

A/improve-codebase-architecture→ 리팩토링 후보 HTML 리포트▶
무엇을 용어집과 ADR을 근거로 얕은(shallow) 모듈·개선 후보를 발굴해 HTML 리포트로 만듭니다. 채택한 후보는 finding → cycle → goal 파이프라인으로 흘려보내 실행합니다 — 리팩토링도 같은 검증 루프를 탑니다.
🏗️ 쉬운 풀이 — 정기 건물 안전점검. 발견된 보수 항목은 즉석에서 고치지 않고 정식 공사 절차(finding→cycle→goal)에 태웁니다.
B/spec-sync계약 ↔ 코드 ↔ ADR 드리프트 정합▶
무엇을 계약문서(spec)와 실제 코드·최신 ADR 사이의 어긋남(드리프트)을 점검합니다. 문서만 고치면 되는 건 직접 갱신, 코드를 고쳐야 하는 건 finding으로 큐잉, 모호하면 질문. 잊어도 시스템이 알려줍니다 — diagnose.sh가 임계(20커밋) 초과 시, completion-check가 전체 완료 시점에 권고합니다.
🗺️ 쉬운 풀이 — 건물은 증축했는데 도면이 옛날 것이면, 다음 시공자(AI)가 옛 도면을 보고 엉뚱한 벽을 뚫습니다. 도면을 현실에 맞추는 작업입니다.
C/roadmap→ dashboard/roadmap.html 시각화▶
무엇을 이슈·active goal·게이트 상태를 읽어 로컬 대시보드(개발 로드맵 DAG + 서비스 흐름 2탭)를 생성·열람합니다. 진행 상황을 코드가 아닌 그림으로 봅니다.
🗺️ 쉬운 풀이 — 공정표 게시판. 어디까지 왔고(초록), 지금 어디를 짓고 있고(화살표), 무엇이 남았는지(회색) 한눈에.

🛡️ 대시보드 ≠ 검증 — Worktree Safety▶
대시보드 출력은 작업 폴더가 깨끗하거나 완성됐다는 증명이 아닙니다. 로드맵을 상태 보고 자료로 쓰기 전에 bash scripts/completion-check.sh를 돌려 게이트 체인을 직접 확인하세요.

스킬 사전

14개의 스킬, 각자의 원리

스킬(skill)은 에이전트가 특정 작업 방식을 따르도록 하는 절차 묶음입니다 — 요리로 치면 레시피. 카드를 눌러 펼치면 작동 원리와 쉬운 풀이가 나옵니다.

/grillPhase 1
계획을 도메인 모델과 충돌시켜 다듬는 그릴링 세션 — 결정표면을 체크리스트로 정산하고 용어집·ADR을 갱신
작동 원리 계획을 기존 문서·결정과 대조하며 모순과 빈칸을 캐묻습니다. 핵심 장치 넷 — ① 결정표면 회계: 엔티티마다 4렌즈(구조: 1:N인가? / 행위: 수명주기·동시성 / 기술: 저장·인터페이스 / 계약: 상태값 집합·유일성)를 돌려 답해야 할 결정을 docs/grill/checklist.md에 전부 열거하고 슬롯별 상태를 추적. ② 4상태 닫힘: 각 슬롯은 [x] 결정 / [~] 보류 / [>] 실험 대기 / [-] 렌즈 해당없음 중 하나로 닫힘. 빈칸도 미해결 [>]도 없으면 "기능 X 닫힘 — /freeze ready"를 선언. ③ grounds-gate: 질문이 사용자에게 도달하려면 "어느 슬롯 · 왜 기존 재료로 안 풀리나 · 오답의 대가" 3요소를 대야 함 — 노이즈 질문 차단. ④ 문서 강등: 외부에서 가져온 기획서는 진실이 아니라 "도전 가능한 재료"로 취급 — 언급(touched)과 규칙으로 서술(covered)을 구분.
산출물 docs/grill/checklist.md(결정표면 정산) · CONTEXT.md(용어집) · docs/adr/(결정 기록, 드물게)
🔥 비유하면 깐깐한 건축사 인터뷰입니다. 다만 아무거나 묻지 않습니다 — 도면에서 유추되는 건 안 묻고, 잘못 추측하면 비싼 결정만 골라 묻습니다. "충분히 물은 느낌"이 아니라 "체크리스트의 모든 칸이 닫혔음"이 종료 조건이며, 닫히면 /freeze로 넘길 수 있습니다.
/freezePhase 1bespoke
닫힌 기능 하나를 한 번의 호출로 PRD·계약·이슈·graph-lint까지 봉인하는 sealed 오케스트레이터
작동 원리 grill이 "닫힘"을 선언한 기능을 단 한 번의 호출로 봉인합니다 — 이 호출 자체가 유일한 인간 승인점입니다. 내부에서 순서대로 ① 2방향 의도감사(비저자 서브에이전트가 처분 + 잔여 항목 열거로 채워진 추측 사냥) → ② to-prd(의도 사진) → ③ spec 생성 / 증분확장(없으면 0→1 생성, 있으면 충돌 검사 후 확장) → ④ to-issues(수직 슬라이스 + depends/risk frontmatter) → ⑤ graph-lint(scripts/issues-graph-check.sh로 순환·dangling 하드 게이트)를 돌립니다. sealed 모드라 번들 도중 사용자에게 되묻지 않습니다 — 모든 미결정은 grill 체크리스트에서 이미 닫혀 있어야 하며, 봉인은 기능 단위(tracer-bullet)로 한 번에 하나씩 찍습니다.
호출 Claude: /freeze (Codex 미설치 — 기획 스킬) · 산출물: docs/prd/PRD.md · docs/spec/* · docs/issues/NNN-*.md
📜 비유하면 계약서 묶음(PRD·계약·이슈)에 도장을 한 번 찍는 절차입니다. 도장 직전 제3자가 "정말 합의된 조항입니까?"를 검토하고, 서류끼리 앞뒤가 맞는지(graph-lint)를 기계가 확인합니다. 도장 한 번이 곧 사람의 승인이라, 그 안에서는 더 묻지 않습니다.
/prototypePhase 1선택
설계 확정 전에 버리는 시제품으로 질문에 답을 얻는 스킬
작동 원리 질문 유형으로 두 갈래를 자동 선택합니다 — 상태·비즈니스 로직 질문이면 실행 가능한 터미널 앱(데이터가 실제로 어떻게 흐르는지 만져봄), UI 질문이면 과감하게 다른 변형 여러 개를 한 라우트에서 토글(한 개 만들어 정붙이는 것 방지). 프로토타입은 시작 전에 "무슨 질문에 답하려는가"를 한 문단으로 명시합니다 — 답이 나오면 코드는 버리고 답만 설계에 반영.
산출물 버리는 코드 + 설계 결정에 들어갈 "답"
🧪 종이 모형입니다. 모형을 본 건물에 붙이지 않듯, 프로토타입 코드를 본 코드에 흡수하지 않는 것이 규율입니다.
/to-prdPhase 1
대화 맥락을 PRD(제품 요구사항 문서)로 굳혀 발행
작동 원리 grill까지의 대화에서 합의된 요구사항을 구조화된 PRD로 추출해 이슈 트래커(이 템플릿에서는 docs/prd/PRD.md 로컬 파일)에 발행합니다. PRD는 "원래 의도"의 고정 사진 — 이후 구현이 바뀌어도 PRD를 고치지 않고, 현재 상태의 권위는 spec이 갖습니다.
호출 경로 이제 /freeze가 sealed 번들로 내부 호출합니다 (개별 단계 아님).
산출물 docs/prd/PRD.md
📸 "처음에 무엇을 왜 만들기로 했나"의 기념사진. 항해 중 길을 잃으면 돌아보는 원점이지, 매일 보는 지도(spec)가 아닙니다.
/to-specPhase 1bespoke
PRD·ADR을 계약문서(docs/spec/)로 처음 생성 — 0→1 전용
작동 원리 승인된 ADR + PRD + 용어집을 읽어 데이터 스키마 · API 계약 · 도메인 타입 등 코드가 반드시 따르는 안정 인터페이스를 추출하고 INDEX.md로 묶습니다. "현재 계약 = INDEX.md가 가리키는 것만"이라는 권위 규칙으로, 구현 에이전트가 무엇을 최우선으로 읽을지 못 헷갈리게 만듭니다. 생성 전용입니다 — 이후 유지보수는 /spec-sync 담당(역할 분리).
호출 경로 이제 /freeze가 sealed 번들로 내부 호출합니다 (개별 단계 아님 — 없으면 0→1 생성, 있으면 증분확장).
산출물 docs/spec/data-schema.md · api-contract.md · domain-types.md … + INDEX.md
📜 시공 계약서 작성입니다. 도장 찍은 뒤(동결 후)에는 구현이 이 계약서를 "단일 진실"로 따르고, 현실과 어긋나기 시작하면 spec-sync가 개정 절차를 밟습니다. 이 템플릿 전용으로 만든 스킬이라 공개 출처가 없습니다.

/tdd보조
red-green-refactor 테스트 설계의 깊이를 보강 — build과 택일 아님
작동 원리 TDD 절차 자체는 build에 내장돼 있습니다. 이 스킬이 더하는 건 "어떻게 도는가"가 아니라 "무엇을 왜 그렇게 테스트하나" — 구현 세부가 아닌 공개 동작을 검증해 리팩토링에도 살아남는 테스트, 깊은 모듈 인터페이스 설계, mocking 가이드. 테스트 설계가 까다로운 기능이나 goal 루프 밖 단발 작업(버그 수정, 프로토타입)에서 따로 부릅니다.
🧰 build이 "공정 순서를 아는 작업자"라면, /tdd는 "검사 항목을 어떻게 정해야 하는지 아는 품질 엔지니어"입니다. 평소엔 작업자로 충분하고, 검사 설계가 어려운 부품에서 엔지니어를 부릅니다.

채널 1 — 스킬

install-skills.sh

템플릿 루트에서
# 새 머신: 빠진 것만 설치 (기존은 skip)
$ bash scripts/install-skills.sh

# 템플릿에서 스킬을 고친 뒤: 전역 재배포
$ bash scripts/install-skills.sh --force

# 확인
$ ls ~/.claude/skills   # Codex 세트는 ~/.codex/skills
⛔
원 출처에서 재설치 금지. 레포 사본에는 템플릿 전용 수정(dryforge 이식 · escalation ladder · EXAMPLE.md 연결 등)이 들어 있습니다. 공개 출처(mattpocock/skills, greatSumini/cc-system)에서 다시 설치하면 수정분이 덮입니다. 정본 = 레포 skills/.
✍️
스킬 수정의 정규 경로: 레포 skills/에서 고친다 → --force로 전역 재배포 → 커밋. 전역 폴더를 직접 고치면 레포 백업과 어긋나 다음 설치 때 유실됩니다.
채널 2 — 자산

update-workflow.sh — 3-way 동기화

기준점은 .workflow-version 마커(프로젝트가 마지막으로 수용한 템플릿 커밋 SHA). "프로젝트가 고쳤나 / 템플릿이 전진했나"를 파일별로 비교해 안전한 것만 자동 적용합니다.

구버전(v0) 프로젝트 첫 적용
$ cd <프로젝트>
# 1) dry-run 보고 (기본 — 아무것도 안 바꿈)
$ bash <템플릿>/scripts/update-workflow.sh --from <템플릿>
# 2) 신규 생성 + 안전 갱신만 적용
$ bash <템플릿>/scripts/update-workflow.sh --from <템플릿> --apply
# 3) [REVIEW]/[CONFLICT]를 안내된 명령으로 정리한 뒤 기준점 기록
$ bash scripts/update-workflow.sh --set-baseline
이후 일상 업데이트
# --from은 마커에 기억됨 — 인자 불필요
$ bash scripts/update-workflow.sh           # dry-run 보고
$ bash scripts/update-workflow.sh --apply   # 적용

# --from은 로컬 경로·git URL 둘 다 가능
# exit 0 = 깨끗 / 1 = 사람 판단 필요 / 2 = 사용법 오류

파일별 판정 — 무엇이 어떻게 되나

판정상황동작
[OK]로컬 = 템플릿이미 동기화 상태 — 아무것도 안 함
[NEW]템플릿에 새 파일--apply 시 생성
[UPDATE]프로젝트는 안 고쳤고 템플릿만 전진--apply 시 자동 갱신
[LOCAL-MOD]프로젝트가 고쳤고 템플릿은 그대로커스텀 유지 (예: 스택 맞춤 _meta.gates.sh)
[CONFLICT]둘 다 고침덮지 않고 보고만 — 안내된 명령으로 수동 정리 후 --set-baseline
[LOCAL-DEL]프로젝트가 의도적으로 지운 파일삭제 존중 (예: 부트스트랩으로 지운 0-example)
[REVIEW]마커 없는 첫 실행 + 내용 다름보고만 — 사람이 템플릿 채택 / 로컬 유지 선택
🚀
커밋 = 배포 단위. 자산 동기화는 템플릿의 커밋(HEAD) 기준입니다 — 미커밋 변경은 전파되지 않습니다. 새 하네스 파일을 만들면 workflow-manifest.txt에 등재 + 커밋까지 해야 배포됩니다.
🔒
불가침 — 절대 건드리지 않는 것. docs 내용물 · 번호 goal · cycles 이력 · CONTEXT.md · docs/state/* · scripts/smoke.sh. 이것들은 manifest에 등재 자체가 금지된 프로젝트 고유 자산입니다.
👀
첫 적용 팁 — dry-run의 [NEW] 목록을 한 번 훑으세요. 이미 변환을 끝낸 프로젝트에 교육용 0-example이 다시 깔릴 수 있는데, 적용 후 지우면 됩니다 — 마커가 생긴 다음부터 그 삭제는 [LOCAL-DEL]로 영구 존중됩니다.

onboard-codebase (가칭)

템플릿 없이 시작된 기존 코드베이스를 이 워크플로우에 태우는 온보딩 스킬입니다. 현재는 미구현 — 대규모 기존 코드베이스가 생기는 시점에 만듭니다.

계획된 골격: SCAN(스택·모듈·검증 명령·git 이력 자동 파악) → 위험가중 ELICIT(코드가 증언하지 못하는 것만 질문 — 도메인 불변식·보안 경계) → 산출(AGENTS.md 2섹션 + CONTEXT.md 초안 + docs/spec 역추출 + 스택 맞춤 게이트 + 초기 findings 큐). 그때까지 새 프로젝트는 Phase 0 부트스트랩(폴더 복사)으로 시작하세요.

새 프로젝트를 시작하시나요?

폴더 복사 → 초기화 → 기획 체인까지, 시작 절차는 ① 탭의 Phase 0 부트스트랩에 정리되어 있습니다.
